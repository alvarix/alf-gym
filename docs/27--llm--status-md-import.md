## What it does

Two entry points (changed from initial v0 spec after user feedback — see "Spec deviations" below):

**A) Day-scoped (primary)** — `↧ import md` button on the Day view:
1. Click button on a Day → navigate to `#/import-md/d/<dayId>`. Route resolves the Day and parent Workout, displays them in the breadcrumb.
2. Paste/file-pick `.md`, click **parse**. The workout name input is hidden (irrelevant — only the blocks land in this Day).
3. **Add blocks to day** opens a Dexie transaction on `blocks + prescriptions` only, computes `next order = max(existing) + 1`, appends parsed blocks under the target Day.
4. On success, navigates back to `#/w/<workoutId>/d/<dayId>`.

**B) New-workout (direct URL)** — `#/import-md`:
1. Navigate directly. Workout name input shown, pre-filled from the `# Heading` in the file.
2. **Create draft workout** opens a Dexie transaction on `workouts + days + blocks + prescriptions`, creates a draft Workout + Day A + Blocks.
3. On success, navigates to `#/w/<newWorkoutId>`.

In both cases:
- `exerciseId: null` on every prescription.
- The block-view edit form pre-fills `exerciseQuery` from `p.name` so mapping to canonical Exercises is one omnibox click.

## Spec deviations

The `docs/27--llm--md-import.md` spec said **always create a new draft Workout** and explicitly deferred "merge into existing" to v1. After implementation, user feedback was that the natural workflow is:
1. Create Workout (e.g. "9.2") manually
2. Add a Day (e.g. "eg10") manually
3. Import the `.md` content **into that existing Day**

So the day-scoped entry point was added (Option B from the planning conversation, ~30min of additional work). The new-workout flow is kept reachable by direct URL but no longer has a UI entry point on the workouts list.

This is technically a partial implementation of the v1 "merge into existing Workout" feature, scoped down to "append blocks into existing Day" — which is what the user actually wanted.

## Decisions made during implementation

1. **Did not extract `fieldsFromToken` from app.js.** The existing in-app notation parser treats `!` as a "notable" flag — v4 treats `!` as a load terminator. Reusing it would have required a runtime mode flag or destructive rewrite of the en/syn editing path. Wrote a fresh ~80 LOC notation parser inline in `parser.js`. Duplication beat coupling here.
2. **`name` field stored on every prescription** alongside `exerciseId: null`. Adapted `editExercise()` in app.js so `exerciseQuery` falls back to `p.name` when `exerciseId` is null — makes imported workouts immediately usable.
3. **Deep-clone before Dexie write.** `JSON.parse(JSON.stringify(mdImportPreview))` strips Alpine reactive proxies (same fix the JSON import postmortem documented).
4. **Synthetic fixture.** The user's raw 9.2B vault file was not pasted into this session. Built a representative fixture that exhibits all 13 deviations from the LLM spec's deviation table.
5. **Tests use Node's built-in test runner** (`node:test`) instead of adding Jest/Vitest. Zero new deps.

## Known issues / risks

- **Notation tokens must be contiguous** (no spaces). `:20! 20-3` → captured as notes; `:20!20-3` → parsed. Matches the spec but should be revalidated against a real vault file.
- **Free-text prose blocks** (e.g. "Substitution guide for future KB swaps:") under a `### Notes` sub-block currently render with `subLabel = 'Notes'` but the prose itself attaches to the block description (correct per spec).
- **Block description and prescription order interleaving:** if a block has prose *between* prescriptions (not just at the top), the prose attaches to the previous prescription's notes. This is the documented behavior, but worth confirming on real input.
- **No source-range highlighting in preview.** Listed as deferred-to-v1 in the spec; not implemented.
- **No `_unparsed` rows surfacing in the preview.** The AST has an `_unparsed: []` field on every prescription, but the parser never populates it in v0 — anything weird falls into `notes`. The preview's "red rows for unparsed" affordance from the LLM spec is therefore inert. Acceptable for v0; revisit when a real vault file shows up.
